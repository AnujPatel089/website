Business Problem

Fraud Detection Is an Imbalanced-Risk Problem

A fraud model has to identify rare suspicious transactions without overwhelming analysts or legitimate customers with false alarms. This project treats threshold selection and operational reliability as first-class engineering decisions rather than relying on raw accuracy alone.

Rare Positive Class

The training split contains 7,879 legitimate transactions and 121 fraud cases, so class imbalance is central to model design and evaluation.

Decision Trade-off

Precision measures how many flagged transactions are actually fraudulent; recall measures how much fraud is captured. Threshold tuning explicitly balances both.

Decision Support

The application is a portfolio prototype for analyst support, not an autonomous system for declining transactions or restricting accounts.

Data & Feature Engineering

10,000 Transactions with Behavioral Risk Signals

The source dataset contains 10,000 rows and ten original columns, including transaction amount, hour, merchant category, foreign-transaction status, location mismatch, device trust, recent transaction velocity, age and the fraud label.

Original Inputs

  • Transaction amount and time
  • Merchant category
  • Foreign transaction indicator
  • Location mismatch indicator
  • Device trust score
  • Velocity over the previous 24 hours
  • Cardholder age

Engineered Signals

  • High-amount flag
  • Night-transaction flag
  • High-velocity flag
  • Low-trust-device flag
  • Composite rule-based risk score
  • One-hot merchant-category encoding
Split strategy: a stratified 80/20 train-test split preserves the rare fraud class. SMOTE is applied to the training data for model development, while held-out test results remain measured on the original imbalanced distribution.

Model Development

Random Forest with Class Balancing and Threshold Optimization

The selected Random Forest uses 300 trees, maximum depth 10, balanced class weights and random state 42. The notebook compares models and then tunes the fraud classification threshold using precision, recall and F1 on the held-out test set.

Engineering Evidence

More Than a Notebook

The repository includes a reusable Python package around inference and operational checks, plus a Streamlit application, model artifacts, automated tests, Docker configuration and a GitHub Actions quality pipeline.

Trusted Model Artifacts

The inference layer checks that model, feature-column and threshold files exist, match metadata filenames and pass SHA-256 integrity validation before loading.

Input & Output Validation

The service validates transaction input, aligns encoded columns with the trained model schema, verifies probability shapes and rejects non-finite or out-of-range scores.

Operational Health

The application evaluates model, metadata, analytics data and optional SHAP availability and distinguishes healthy, degraded and unhealthy states.

Explainability

SHAP TreeExplainer is used to expose feature-level model behavior for scored transactions. Explanations are presented as model behavior, not causal claims.

Quality & Security CI

GitHub Actions is configured to run Ruff lint/format checks, mypy, Bandit, dependency auditing, pytest coverage and a Docker build on pushes and pull requests.

Test Coverage

The committed Cobertura report shows 394/394 package lines and 96/96 branches covered—100% line and branch coverage for fraud_platform.

Containerization: the repository includes a Dockerfile for the Streamlit application and CI verifies that the image can be built.

Limitations & Repository Status

What Still Needs Production Hardening

Model / Product Limits

  • Custom educational dataset may not represent real banking traffic
  • Fraud behavior can drift over time
  • False positives and false negatives remain unavoidable
  • Displayed model scores are not documented as calibrated probabilities
  • Real deployment would need security, privacy, governance and retraining controls

Current Repository Caveat

The repository’s latest main snapshot contains unresolved merge-conflict markers in the README and Streamlit app. The notebooks, model artifacts, package modules, tests and CI configuration still provide strong project evidence, but the application should be cleaned before presenting the repo as a runnable production-style demo.
